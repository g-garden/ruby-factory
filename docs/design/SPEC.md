# def pack(belt) ゲーム仕様書

土台は、設備を買い足して流量を上げる放置系（インクリメンタル）の工場ゲーム。そこに次の要素を足している。

- Gemfile 形式の研究画面と bundle install 演出、12 月 25 日のリリースで終わる構成、VM のロード中や再起動中も JS で工場を回し続けること、不正な出荷を差分で見せること
- 自分のコードに出てくるメソッドを精錬所の中の機械として並べる表示、Ruby の本物のエラー文をその場で実行して見せる研究カード
- お金で直す場合とコードで直す場合の効き目を並べる診断カード、`rescue => e` で捕まらない監視用の例外、固定シードのベンチ

数値は全部、下の「検証済みのこと」にある実測とシミュレーションから取っている。

## 0. 検証済みのこと

リポジトリにあるもの:

- `vendor/ruby.wasm`: @ruby/4.0-wasm-wasi 2.10.1 の stdlib なし版。17.2MB、gzip すると 5.1MB。`RUBY_VERSION` は `"4.0.0"`。
- `vendor/ruby-wasm-browser.umd.js`
- `src/ruby/runtime.js` と `src/ruby/worker.js`: Module を使い回す再起動と見張りの骨組み。

Node 24 上で、この ruby.wasm を使って次を確認した。

| 512 個のバッチを 1 回処理（6 章のコードすべて） | 1.9〜4.4ms |

## 1. タイトル・一言ピッチ

**def pack(belt)**

サブタイトルは「Ruby で磨く宝石工場」。

原石がベルトを流れ続ける放置系の工場ゲーム。精錬所の中身は、自分で書く `def pack(belt)` の 1 メソッドだけ。

- `each_slice` を足すと稼ぎが 3 倍、`group_by` でさらに 3 倍、`chunk_while` でストレートを組むと 8 倍になる。クリスマス便（carat の合計 25 で ×4）では、窓を値段の高い順に取る 1 行でさらに 3 倍になる。1 行の Ruby が倍率になり、1 鉱石あたりの単価が $1 から $330,000 まで伸びる。
- 書き方が遅いと精錬所が詰まる。`sort { }` を `sort_by` に変えると精錬所が速くなる。
- 最後は 12 月 25 日、自分の工場で Ruby をリリースして終わる。

タイトルは、プレイヤーが書くメソッドの 1 行目そのもの。ベルト（belt）を受け取って箱に詰める（pack）のが、このゲームでやることのすべてになる。

## 2. コアループ（1 分間で何をするか）

2 つのループを重ねる。

**10 秒ループ（眺めて、買う）**

1. 鉱山 → ベルト → 精錬所（`pack`）→ 出荷ドックの順に原石が流れる。箱が出るたびに「+$960」のようなポップが出る。
2. 4 工程のうち一番遅い 1 か所（ボトルネック）が赤く脈打つ。手前に原石が積もる。
3. 赤い工程をクリックすると診断カードが開く。「サーバー +1 ($8.6k) で +33%」「鑑定を 1 回減らすと +136%」のように、お金で直す場合とコードで直す場合の効き目が並ぶ。
4. 買う。流量が上がり、別の工程が赤くなる。

**1〜3 分ループ（書く）**

1. 研究（Gemfile に 1 行足す）で新しい値付けルールや素材が開く。研究カードにはヒントのメソッド名と短い使用例が出る。
2. エディタで `pack` を書き換え、Cmd/Ctrl+Enter でデプロイする。
3. 固定シード 3 本 × 512 個で、前のコードと新しいコードのベンチを取る。benchmark-ips 風の倍率バナーを出す。
4. 単価が上がると、流量 × 単価で $/s が桁で跳ねる。代わりに鑑定回数（CPU 負荷）が増えて、精錬所が赤くなることがある。
5. 対処は 2 つ。CPU を買うか、鑑定の少ない書き方に直すか。そして 10 秒ループに戻る。

1 分の中で「眺める、買う、赤を見つける、直す」が数回、「書く、デプロイ、倍率バナー」が 0〜1 回起きる密度を狙う。

## 3. 起動直後の 30 秒と最初の 10 分

### 3.1 最初の 30 秒

前提:

- ページを開いた瞬間に、メインスレッドで ruby.wasm の取得とコンパイルを始める。
- Ruby の準備ができる前は、JS が「素通し」で工場を回す。未梱包の原石は 1 個 $1 で売れ、ドックの枠を使わない（バラ積みシュートで出荷する）。
- **初回デプロイの解禁条件は「VM の準備完了」かつ「つるはし 5 本」**。エディタはロード中から見えていて編集もできるが、デプロイボタンは条件がそろうまで「つるはし 5 本で精錬所が動きます。あと 2 本」と表示する。こうしておくと、デプロイ直後の採掘が 2.5 個/秒以上になり、ドック（2 箱/秒）が必ず赤くなる。VM が数秒で準備できる速い回線でも、この見せ場が崩れない。
- 下の秒数は、シミュレーションで「クリック 1 回/秒を 30 秒続ける」とした場合の値。VM の準備が 3 秒でも 8 秒でも 25 秒でも、同じ 27 秒に初回デプロイになった。

初期コード:

```ruby
# belt には原石が 512 個流れてくる。
# 返した配列の要素 1 つが 1 箱になる。
# 原石は color・carat・flaw を持つ。
# pack に p belt.first と書くと見える。
# 属性を読むほど鑑定が増えて精錬所が詰まる。
def pack(belt)
  belt.map { [it] }   # 1 個ずつ箱に詰める
end
```

クリックしない人の場合（シミュレーション: クリックなし）:

- つるはしを 20 秒、35 秒、45 秒、55 秒ごろに買い足し、$/s は 0.5 → 2.5 に伸びる。
- 初回デプロイは 56 秒（VM が 3 秒で準備できた場合）〜60 秒（VM の準備が 60 秒かかった場合）。定量梱包 I は 1:00〜1:03 に買える。
- 解禁条件を「つるはし 5 本」にしない場合（VM 3 秒、条件なし）は、3 秒で初回デプロイしても採掘 1.5 個/秒でドックは赤くならず、定量梱包 I を 0:09 に買っても解消するものがない。これを避けるための条件である。

## 5. エンティティと数値

数値はすべて `data/balance.js`（1 ファイル）にまとめ、シミュレーションと同じ表を読む。購入型の設備の値段は、1 台買うごとに ×1.15 になる。

### 5.1 通貨

- $（ドル）1 種類だけ。
- 表示は 1,000 未満は整数、それ以上は K / M / B / T / Qa / Qi、さらに上は `1.23e18`。
- 「単価の記録」は、これまでに HUD に表示した単価（5.7 節の移動平均）の最高値。バッチを受け取るたびと、研究で値付けし直したときに更新する。デプロイのときだけ更新するのではない（定量梱包 II やサファイアのように、コードを変えずに単価が上がる研究があるため）。研究の解禁条件に使う。

### 5.2 資源（原石）

```
Ore = Data.define(:id, :color, :carat, :flaw)
```

- carat: 1〜9 の一様分布。
- flaw: 25% の確率で true。
- color: 研究で増える。赤 1、青 2、緑 4（色単価）。開いている色の中から一様に選ぶ。

| 色 | 色単価 | 解禁 |
|---|---|---|
| 赤（ルビー） | 1 | 最初から |
| 青（サファイア） | 2 | 研究「サファイア鉱脈」 |
| 緑（エメラルド） | 4 | 研究「エメラルド鉱脈」 |

CPU の値段は、`sort { }`（鑑定 6.96 回）をお金だけで直すと高くつき、`sort_by`（1.74 回）に直すと赤が消える高さに置いている（8.4 節）。

研究による補正:

- Ractor: CPU 全体 ×4。
- YJIT: 鑑定コスト ×0.5（実測の鑑定回数に 0.5 を掛ける）。

精錬所の処理量 = CPU ÷（鑑定回数/鉱石）。鑑定回数は max(実測, 監査ライン)。0 回で無制限になるのは、ボーナスが偶然の範囲に収まるコード（`each_slice` だけなど。監査ラインが 0 になる）だけ。ボーナスのそろった箱を 1〜2 箱だけ混ぜても、売上の下限（偶然ではまずそろわない箱の売上を、正直な詰め方の鑑定 1 回あたりの売上 × 2 で割った回数）からラインが付く。監査ラインは JS が出荷された箱のボーナスと、同じベルトで作る基準解から引く。研磨した原石が k 個出荷されていれば、1 + 2 + … + k 回を足す（SPEC-rubyist 3.2）。

- 箱が大きいほど、同じ原石数に対して箱数が減り、ドックの負荷が下がる。
- 素通し中（初回デプロイ前）の未梱包の原石はドックを使わない。

### 5.7 流量と収入

```
採掘    = Σ設備 + クリック
ベルト  = 現在の段階の容量
精錬所  = CPU × 研究補正 ÷ (max(実測, 監査ライン)/鉱石 × YJIT補正)   # 0 回なら ∞（監査ラインが 0 のときだけ）
ドック  = ドック箱/秒 ÷ (有効な箱数/鉱石)                  # 素通し中は ∞
流量    = min(採掘, ベルト, 精錬所, ドック)                 # 個/秒
収入/秒 = 流量 × 単価($/鉱石)
```

- 鑑定回数/鉱石、有効な箱数/鉱石、単価は、直近 5 バッチの指数移動平均（α = 0.4）を使う。
- 流量の計算と描画は JS が 60fps で行う。Ruby を呼ぶ頻度は流量に依存しない。

### 5.8 箱の値段（JS 側で計算）

```
箱の値段 = Σ(carat × 色単価) × 箱の個数 × ボーナス
```

ボーナス（研究で開いたものだけ掛ける）:

| ボーナス | 倍率 | 条件 |
|---|---|---|
| 無傷 | ×3 | 箱の全原石が flaw=false か、研磨済み |
| 単色 | ×3 | 箱の全原石が同じ色 |
| 昇順 | ×2 | 個数 2 以上で、返した順に carat が単調非減少 |
| ストレート | ×2^(個数-1) | 個数 3 以上で、返した順に carat が 1 ずつ増える |
| クリスマス便 | ×4 | 箱の carat の合計がちょうど 25。並び順や個数は問わない |

ボーナスはすべて掛け算になる。3,4,5,6,7（同色・無傷）の箱は 無傷 ×3・単色 ×3・昇順 ×2・STRAIGHT ×16・クリスマス便 ×4 がそろう。5,5,5,5,5 にはクリスマス便が付くが、STRAIGHT は付かない。金縁の PERFECT は、これまでどおり無傷・単色・昇順・STRAIGHT の 4 つで決める（7 連・9 連のストレートは合計 25 にならないため）。

次の箱は無効で $0 になり、「スクラップ」として数える。

- 個数が 0、または `box` を超える
- id が存在しない、または Ore 以外の要素を含む
- 同じ原石が 2 回以上出荷されている。後から出てきた箱を無効にする

箱に入らなかった原石もスクラップ（$0）になる。

## 6. プレイヤーが書く Ruby

### 6.1 入出力の契約

プレイヤーが書くのは `def pack(belt)` の 1 つだけ。ヘルパーメソッドや定数は自由に足してよい。ファイル名は `pack.rb` として eval する。

| 項目 | 内容 |
|---|---|
| 引数 `belt` | 原石の Array（512 個、frozen）。要素は `Ore`（`Data.define(:id, :color, :carat, :flaw)`）。color は `:red` / `:blue` / `:green` |
| 戻り値 | 原石の配列の配列。中の配列 1 つが 1 箱になる |
| `box` | トップレベルのメソッド。いまの箱サイズの上限（1, 3, 5, 7, 9）を返す |
| `ore.polish` | 研究「研磨機」で解禁。その原石の傷を消した扱いにする（JS が id で記録する）。戻り値は同じ原石。磨くほど研磨機が熱くなる（下の鑑定の項） |
| `Yield.heat` | いまの研磨機の熱（このバッチで磨いた回数）。`p Yield.instance_variables` にも `:@heat` が出る |
| `puts` / `p` / `print` | ログ欄に出る。1 バッチ 4KB まで。トップレベル（def の外）の出力も、デプロイ時にログ欄に出る |

鑑定（CPU コスト）:

- `color` / `carat` / `flaw` を 1 回読むたびに 1 回。
- `to_h` / `inspect` / `to_s` / `==` / `eql?` / `hash` / `with` は 3 回。`deconstruct_keys` は読んだキーの数だけ。
  - 比較とハッシュも数えるのは、`belt.group_by { it.with(id: 0) }` で属性ごとにまとめると鑑定 0.21 回/鉱石で整列・仕分けができてしまうため（数えると 9.23 回になる。wasm で確認）。
- `polish` は研磨機の発熱で決まる。1 バッチの中で n 回目の研磨は鑑定 n 回なので、k 回磨くと 1 + 2 + … + k = k(k+1)/2 回。熱はバッチの頭で 0 に戻り、次のバッチに持ち越さない（ベンチでも本番でもリロードのあとでも、1 回目の研磨は 1 回）。
  - 熱は `Yield` の `@heat` に持つ。研磨 1 回ごとに `Yield.heat_up` が熱を 1 上げ、上がった熱の数だけ鑑定する。
  - `@heat` を書き換えて冷やすことはできる。ただし整数でない・負・ここまで磨いた回数より大きい値は、冷えた研磨機として 0 から数え直す。鑑定が 0 未満になったり、書き換えた値で Overheat になったりはしない。冷やした分は監査が研磨した数から数え直す（下の禁止事項の表）。
  - 冷やしたかどうかは `Yield.cooled?` で分かる。正直に磨いていれば、バッチの終わりの `@heat` は磨いた回数（同じ原石を 2 回磨けば 2 回）と同じになる。書き換えるとこれがずれる。
  - 箱 9・3 色で傷物を全部磨いても、512 × 3 + k(k+1)/2 回で上限の 200,000 回には届かない。
- 原石を見ないで動かすだけ（`each_slice` など）は無料。だから「原石の属性を何回読むか」がそのまま工場の処理能力になる。
- 1 バッチの上限は 200,000 回。超えると `Yield::Overheat` になる。

禁止事項と、どう効くか（すべて JS 側の検算で止める）:

| やったこと | 結果 |
|---|---|
| 同じ原石を複数の箱に入れる（`[belt.first(3)] * 1000`） | 2 回目以降の箱は無効。ログに「id 0, 1, 2 が 1000 回出荷されています。複製は無効です」と差分で出す |
| 値を書き換える（`it.with(carat: 99)`） | 効かない。値段は JS が id から自分のデータで付ける。`with` で作った Ore も同じ id なので、元の原石として売れる（`with` の分の鑑定 3 回だけかかる） |
| Ore 以外を返す（`[[1, 2, 3]]`） | その箱は無効。「Ore 以外が 3 個入っています」 |
| 配列の配列以外を返す | そのバッチは全部スクラップ。精錬所が「詰まり」表示になる（10.5 節） |
| `box` を超える箱 | 無効。「はみ出し」 |
| `Yield.tick` を再定義して鑑定 0 にする | 書けるが、精錬所の計算に使う鑑定は監査ラインで止まる（SPEC-rubyist 3.2）。実績「モンキーパッチャー」と裏口ノートのページ 4 は残る。判定は `Yield.singleton_class.instance_method(:tick).source_location&.first == "pack.rb"`（wasm で確認。prelude のままなら `"eval"`、再定義すると `"pack.rb"`）。`alias_method(:tick, :box)` のように prelude のメソッドで潰した場合は判定が false のままなので、監査に捕まったときの手口の推定（tick の別名）でページ 4 にする。デプロイごとに VM を作り直すので、パッチは次のデプロイに持ち越されない |
| `super_method.bind_call`、`Data.instance_method(:to_h).bind_call`、`remove_method`、`@ops` の書き換え、`Yield.polished(id)` の直呼びで鑑定を減らす | 監査ラインで止まる。ラインを割ると監査報告（Ruby の warning の形）と AUDITED の判子が出て、裏口ノートのページ 3 が埋まる。罰はない。`Yield.polished(id)` の直呼びは、研磨の下限 1 + 2 + … + k で捕まる |
| `instance_variable_set(:@heat, 0)` などで研磨機を冷やす | 鑑定は減るが、監査は出荷された研磨済みの原石 k 個から 1 + 2 + … + k 回を下限として数える。磨く数が少なくてこの下限に収まるときも、`Yield.cooled?` が true のバッチは、磨いた回数を n として「実測 − n + (1 + 2 + … + n)」を下限にするので捕まる（全部冷やしたときは、正直に磨いた場合の鑑定とちょうど同じ）。報告では鑑定長が「研磨機に水をかけましたね。冷やしても、磨いた数は箱に残っています」と言う。罰はない。`def Yield.heat_up` を再定義すると `patched?` が true になる |

### 6.2 チュートリアルの例題コード

以下はすべて、付録 A の prelude を読み込んだ ruby.wasm（Ruby 4.0.0）で実行して確認した。

(1) 初期コード（単価 $5.0、鑑定 0 回）

```ruby
def pack(belt)
  belt.map { [it] }
end
```

(2) 定量梱包 I（$15.0、鑑定 0 回）。endless 版 `def pack(belt) = belt.each_slice(box).to_a` も動く。

```ruby
def pack(belt)
  belt.each_slice(box).to_a
end
```

(3) 検品（$33.3、鑑定 1.0 回）

```ruby
def pack(belt)
  belt.reject(&:flaw).each_slice(box).to_a
end
```

パターンマッチでも書ける。鑑定回数は同じ。

```ruby
def pack(belt)
  belt.select { it in {flaw: false} }.each_slice(box).to_a
end
```

(4) 整列（$66.4、鑑定 1.74 回）

```ruby
def pack(belt)
  belt.reject(&:flaw).sort_by(&:carat).each_slice(box).to_a
end
```

同じ結果をブロック付きの `sort` で書くと、wasm では鑑定 6.96 回になり、精錬所が約 4 倍遅い。

```ruby
def pack(belt)
  belt.reject(&:flaw).sort { |a, b| a.carat <=> b.carat }.each_slice(box).to_a
end
```

(6) ストレート、chunk_while 版（箱 5 で $4,086、鑑定 3.76 回）

```ruby
def pack(belt)
  belt.reject(&:flaw).group_by(&:color).values.flat_map { straights(it) }
end

def straights(ores)
  pool = ores.group_by(&:carat)
  out = []
  loop do
    run = (1..9).filter_map { pool[it]&.pop }
    break if run.empty?
    out.concat run.chunk_while { |a, b| b.carat == a.carat + 1 }
                  .flat_map { it.each_slice(box).to_a }
  end
  out
end
```

(7) ストレート、each_cons 版（$3,032、鑑定 2.49 回）。`pack` は (6) と同じ。

```ruby
def straights(ores)
```

(10) クリスマス便、窓を値段順に取る版（箱 5・2 色で $14K、鑑定 2.52 回）。`pack` は (6) と同じ。長さ 3〜box の窓を、箱の値段の目安が高い順に取る。箱 5 なら 3..7 の窓（STRAIGHT ×16 とクリスマス便 ×4 で ×64）が先に来る。

```ruby
# 箱の値段の目安。carat の合計 × 個数 × STRAIGHT の倍率。合計 25 ならさらに ×4
def worth(run)
  run.sum * run.size * 2**(run.size - 1) * (run.sum == 25 ? 4 : 1)
end

def straights(ores)
  pool = ores.group_by(&:carat)
  runs = (3..box).flat_map { (1..9).each_cons(it).to_a }
  runs.sort_by { -worth(it) }.flat_map do |run|
    Array.new(run.map { pool[it]&.size.to_i }.min) { run.map { pool[it].pop } }
  end
end
```

(11) 研磨機、箱いっぱいの窓の穴だけ磨く版（`SAMPLE_CODE.polishHoles`。箱 5・2 色で $20K、鑑定 4.80 回）。色ごとに `partition` で傷のない原石と傷物に分け、窓は傷のない原石で埋める。長さ box の窓だけ、足りない carat のところは傷物を `polish` して埋める（`pool[it]&.pop || spare[it].pop.polish`、条件は `run.size == box`）。長さ box の窓は STRAIGHT の倍率が一番大きいので、1 回の研磨で上がる単価も一番大きい。box を読むので、箱 7・9 でも書き換えずに働く。余った原石を色ごと・傷の有無ごとに carat の順で詰める行はコメントにしてある（carat は `group_by` で読んだキーで並べるので、# を外しても鑑定は増えない）。全文は `data/balance.js` にある。

ストレートの手本も、余りと傷物を色ごとに carat の順で詰めて出す形（`SAMPLE_CODE.straightAll`）にした。中身は (6) の chunk_while 版に、傷物の箱を足したもの。

## 8. ボトルネックの発生・可視化・解消

### 8.1 どう生まれるか

流量は 5.7 節の min(...) で決まる。どれか 1 つを上げると次が詰まるように、設備の価格と研究の順番を置いている。シミュレーションで観測した序盤の順番:

1. 0:27〜 ドック: `map { [it] }` は 1 鉱石 = 1 箱なので、箱が多すぎる。直し方は `each_slice`（コード）かトラック（購入）。
2. 1:30 前後 ベルト: 流量が 8 個/秒を超えて黄ベルトが詰まる。直し方は赤ベルト。
3. 1:20 前後 CPU: 検品で鑑定が 1.0 回/鉱石になり、CPU（初期 10 鑑定/秒）が初めて赤くなる。直し方はコアの購入（$500）。
4. 2:30 前後 CPU: 整列で `sort { }` を書くと鑑定が 6.96 回になり、精錬所が長く赤くなる。人間らしい方針の sim（貯めない）では、`sort { }` の 30 秒間ずっと精錬所が赤で、CPU を買い続けても赤が消えるのは 90 秒後。`sort_by` に書き換えると（1.74 回）、その場で赤が消える（精錬所/流入 = 1.76）。研究のために貯めていた人（収入 30〜60 秒分以内なら貯める sim）は、手元のお金で 3〜22 秒で直せる。
5. それ以降は、研磨のあり・なし（エメラルドの段で箱いっぱいの窓の穴だけ磨くと単価 1.4 倍、鑑定 1.9 倍）や、余りの箱を出すか消すかで、どこが赤いかによって有利不利が逆転する。全部磨くと研磨機が真っ赤になり、精錬所も赤くなる。

### 8.2 どう見せるか

- 4 工程それぞれに使用率バー（流量 ÷ その工程の容量）を出す。
- 一番低い 1 か所だけを赤く脈打たせ、「BOTTLENECK」の判子を押す。同率なら下流を優先する。判子は 1.5 秒以上同じ工程に留まったときだけ移す（ちらつき防止）。
- 赤い工程がもう買い足せないとき（最終段のベルト）は、判子は残したまま、ショップの行と診断カードで次の研究までの目安を出す（7 章）。
- 赤い工程の手前のベルトに原石を積み上げる。在庫カウンタを出し、上限（表示上 200 個）を超えた分は「こぼれ: 12 個/秒」と表示して粒子を落とす。
- 赤い工程より上流は彩度を落とし、「待機 63%」を出す。

### 8.3 診断カード

赤い工程をクリックすると、その場にカードを出す。中身は JS が 5.7 節の式に仮の値を入れて計算する。

```
精錬所: 処理 172 個/秒 ／ 流入 410 個/秒
CPU 300 鑑定/秒 ÷ 鑑定 1.74 回/鉱石

お金で直す
  サーバー +1   $8,625   → 収入 +33%
  ラック +1     $125,000 → 収入 +138%（ボトルネックがベルトに移ります）
コードで直す
  鑑定を 1 回/鉱石 減らせたら → 収入 +136%
  ヒント: sort のブロックの中で carat を読んでいます
```

- 「コードで直す」の行は、鑑定回数を 1 減らした場合の試算。ヒント文はコード文字列の簡単なパターン（`sort {`、`sort do`、同じ属性を何度も読むブロック）で選ぶ。
- 各行に購入ボタンを置き、ショップの該当する段にもスクロールする。

### 8.4 どう解消するか

- 購入（すぐ効くが、値段は ×1.15 ずつ上がる）と、コード（無料だが頭を使う）の 2 通りが常にある。
- コードで鑑定を減らしたとき（`sort { }` → `sort_by` など）は単価が変わらないので、倍率バナーの見出しを単価ではなく精錬所の処理量にする（「精錬所 120 → 470 個/秒（3.93x）」）。下の行に鑑定回数の変化と「精錬所の赤が消えます」などの一言を出す。Ractor と YJIT も単価が変わらないので、買ったあとに同じ形のバナーを出す。
- 解消した瞬間は、積もっていた原石を 1.5 秒かけて一気に流す。「+$12,345」のポップを連続で出し、解消そのものを報酬にする。

## 10. ruby.wasm の実行設計

### 10.1 構成

- メインスレッドの JS がゲームの主状態を全部持つ: お金、設備、研究、直近のバッチ結果、最後に成功したコード。
- Ruby は Worker の中で「512 個のサンプル → 箱割り」の純関数として動くだけ。値段表も残高も Ruby 側には置かない。
- `src/ruby/runtime.js` と `src/ruby/worker.js` の作り:
  - wasm はバイト列で取ってから `WebAssembly.compile` する。メモリ上限を書き込むためにバイト列が要るので、`compileStreaming` は使わない。
  - コンパイル済みの Module を Worker に postMessage して使い回す。Worker は classic Worker で、`importScripts` で UMD を読む。
  - 見張りは JS のタイマー（`_send`）で行う。TracePoint の見張りは使わない。0 章のとおり 5〜14 倍遅く、`while true; end` も止められないため。
  - Worker とのやり取りは `deploy` と `batch` の 2 つ。プログラムは `pack` 1 つだけ。
- wasm は stdlib なし版（`vendor/ruby.wasm`、gzip で 5.1MB）を使う。JSON も StringIO も使わない。
- ruby.wasm は同じオリジンの `vendor/ruby.wasm` だけから読む。CDN へのフォールバックは、取ったバイナリを確かめずに動かすことになるので置かない。
- ダウンロードの進み具合は、非圧縮のサイズ（17,219,023 バイト）を分母にする。Pages が圧縮して配信しても 100% を超えないようにするため。
- COOP/COEP も SharedArrayBuffer も使わない。

### 10.2 プロトコル（1 往復 = 1 バッチ）

JS から Ruby へ渡すのは、Ruby の配列リテラル 1 本だけ（512 個で約 9KB）。

```
Yield.run([box, limit, [[id, color_idx, carat, flaw], ...]])
# 例: Yield.run([3, 200000, [[0,0,5,false],[1,1,9,true], ...]])
# color_idx は 0=red, 1=blue, 2=green
```

Ruby からは、`\x1f` 区切りの文字列 1 本が返る。

```
成功: "OK" US ops US polished_ids(カンマ区切り) US crates US log
      crates は箱を ";"、箱の中の id を "," で区切る。Ore 以外は -1
失敗: "ERR" US ops US 例外クラス US メッセージ US pack.rb の行番号 US log
```

コードの渡し方は既存の `rbStr`（UTF-8 を hex にして `pack("H*")`）を使い、`Yield.deploy(src, box)` を呼ぶ。ファイル名は `pack.rb`、入口は `pack` に決め打ち。戻り値は `"OK" US log`（デプロイ時のトップレベルの出力）か `"ERR" US クラス US メッセージ US 行番号 US log`。

成功の文字列は、実装では `"OK" US ops US polished_ids US 箱の数 US crates US log` になっている（箱の数は `[]` と `[[]]` を区別するため。8,192 箱で切ったときは「送った数/返された数」）。研磨機の熱 `@heat` は `run` の頭で 0 に戻す。

成功したバッチのあと、worker は `Yield.patched?`、`Yield.cooled?`（研磨機を冷やしたか。BatchResult の `heatCooled`）、裏口の報告（private_constant の `REPORT`。`[lanes, night, overtime]`）を読み、BatchResult に入れる。`backdoor` は生の値で、丸めは JS（`economy.clampBackdoor`）。

### 10.3 呼ぶタイミング

| タイミング | 呼ぶもの |
|---|---|
| デプロイ時 | 10.4 節のブルーグリーン |
| 定常 | 3 秒に 1 回、新しいシードで `Yield.run` を 1 回。結果から単価・鑑定回数・箱数の移動平均を更新する |
| 研究で `box` が変わったとき | すぐ 1 回 |
| 研究で値付けルールだけが変わったとき | Ruby は呼ばず、直近 5 バッチの結果を JS で値付けし直す |

画面の流れは、JS が直近の結果を流量に合わせて再生する。表示する箱の中身は直近バッチの箱から順に取り出す。流量が 1 個/秒でも 100 万個/秒でも Ruby の負荷は同じ。

### 10.4 デプロイ（ブルーグリーン）

デプロイのたびに新しい VM を作る。前のデプロイのモンキーパッチや定数の再定義が残らないようにするため。

1. キャッシュ済みの Module から新しい Worker を作り、prelude を eval する（Node で 81ms）。
2. `Yield.deploy(src)` を呼ぶ。SyntaxError などはその場で返し、エディタの該当行に出す。新しい Worker は捨て、古い Worker で工場は動き続ける。
3. 固定シード 1, 2, 3 の 512 個ずつでベンチを取る。同じシードを、古い Worker でも並行して流す。
4. どちらも成功したら、新旧の単価と鑑定回数でベンチバナーを出し、新しい Worker を本番にして古い方を terminate する。
5. 新しいコードがベンチで例外を出したら、デプロイしない。エラーを「詰まり」として見せ、古いコードで動き続ける。

見張り時間は、手順 1〜3 の全体で 5 秒。

デプロイは列（`runtime._dq`）に並べるので、同時に何本投げても候補の VM は 1 つずつ立つ。生きている VM は最大 2 つ（本番＋候補）。

### 10.5 タイムアウト、VM 再起動、エラーを「機械が詰まる」表示にする

暴走への備えは 2 段:

1. 鑑定の上限（Ruby 側）。1 バッチで 200,000 回を超えたら `Yield::Overheat` を raise する。`Overheat < Exception` なので、プレイヤーが `rescue => e` と書いても捕まらない（wasm で確認済み）。原石を読み続けるループはこれで止まり、Worker は殺さずに済む。
2. 見張り時間（JS 側）。定常バッチは 2 秒、デプロイは 5 秒。返らなければ `worker.terminate()` し、キャッシュ済みの Module から新しい Worker を作って、最後に成功したコードを読み直す。`loop {}`、`while true; end`、`rescue Exception` で retry し続けるコードはこちらで止まる。Worker の `onerror`（メモリ枯渇など）も同じ経路に流す。

画面での扱い（工場は止めない。最後に成功したバッチの単価・鑑定回数・箱割りで JS が回し続ける）:

| 起きたこと | 精錬所の見た目 | エディタ／ログ |
|---|---|---|
| SyntaxError（デプロイ時） | 変化なし（古いコードで稼働） | 該当行に赤線。Ruby のメッセージをそのまま出す |
| 例外（`NoMethodError` など） | 赤い回転灯と「詰まり」の札。札に例外クラス名 | 故障票: 「pack.rb:2 NoMethodError: undefined method 'slect' for an instance of Array」 |
| `Yield::Overheat` | 精錬所から黒煙。「オーバーヒート」 | 「鑑定が 200000 回を超えました。原石を読み続けるループになっていませんか」 |
| 見張り時間切れ | 煙と「再起動中…」。復帰したら「前のコードで再開しました」 | 「TimeoutError: pack が 2.0 秒以内に戻りませんでした。無限ループかもしれません」 |
| 戻り値が不正 | 黄色の「検品エラー」札 | 差分を出す: 「id 0, 1, 2 が 1000 回出荷されています。複製は無効です」「Ore 以外が 3 個入っています」 |

- 定常バッチで例外が 10 秒に 3 回出たら、そのコードを止める。最後にベンチを通ったコードに戻し、「例外が 10 秒に 3 回出たので、前のコードに戻します。エディタのコードはそのままです」と出す。本番 VM の作り直しが 30 秒に 3 回続いたときも、同じように前のコード（なければ初期コード）に戻す。
- `Yield` に無いメソッド（`Yield.foo` など）を呼ぶと、故障票が「undefined method 'foo' for module Yield。奥から工場長の声「用があるなら、ちゃんと頼め」」になる（prelude の method_missing。裏口ノートのページ 6 の入口）。
- did_you_mean は stdlib なし版に入っていないので、`slect` → `select` のような候補は JS 側で出す。Enumerable と Array のメソッド名の一覧と、編集距離 2 以内で比べる。

### 10.6 精錬所の機械アイコン

stdlib なし版では Prism も `Ripper.lex` も使えない。そのため JS で行う。

1. コード文字列から、コメントと文字列リテラルを正規表現で取り除く。
2. `/\.(\w+[?!]?)/` と `/&:(\w+[?!]?)/` でメソッド名を出現順に拾う。
3. 用意したアイコン一覧（reject, select, sort_by, sort, group_by, values, flat_map, each_slice, each_cons, chunk_while, map, filter_map, partition, polish など）にあるものだけを、精錬所の中に機械として並べる。

### 10.7 セーブデータ（localStorage）

キーは `yield-factory/v1`。5 秒ごとと `visibilitychange` で書く。読み書きは try/catch で囲む。

```js

  money, totalEarned, record,          // record = 単価の記録
  mines: { pickaxe: 3, drill: 1, ... },
```

### 11.3 バランス調整の道具

5 章の表を読むヘッドレスの経済シミュレーションを `tools/econ.mjs` に置いている。数値は次の設定で出した。

- 1 秒刻み。
- クリックは 1 回/秒を 30 秒。VM の準備は 8 秒（3 秒・25 秒・60 秒、クリックなしでも確認）。初回デプロイはつるはし 5 本で解禁。
- 研究はお金が貯まり次第買う。研究価格が「収入の 60 秒ぶん」以下なら、ほかの買い物をせずに貯める。
- それ以外は、いまのボトルネックの工程で「1 ドルあたりの容量増」が最大の設備を買う。
- 研究のたびに、コードを書く時間として 20〜120 秒待ってから新しいコードに切り替える（`--write-scale` で倍率を変えられる。0 なら書く時間なし）。
- 使えるコードの中から、そのときの流量 × 単価が最大のものを選ぶ。30 秒分のお金で CPU を買い足せるときは、買い足した後の収入で比べる（これがないと、箱 9 で研磨なしのコードに張り付いた）。
- 単価・鑑定回数・箱数/鉱石は、econ.mjs の中の表を使う。表は、クリスマス便込みのコード（ストレートは straightAll、クリスマス便は窓を値段順に取る版、研磨機は polishHoles）を JS に移した版で作っている。移植版の単価は ruby.wasm の実測と多くは 1〜3% の差で合い、箱 7 と箱 9 の窓の版では 5% ほどずれる。econ.mjs の表は、箱 7 の窓の版だけ移植版の 46,852 を使っていて、5.9 の表の ruby.wasm の実測 49,376 より 5% 低い。鑑定は ruby.wasm の実測値を使う。

人間のペースは、このボットの 1.5〜1.8 倍遅いと仮定している。プレイテストで直す。

`--policy both` で、ボットと人間らしい方針（貯めない・赤い工程を 1 秒に 3 個まで・コードは 1 本ずつ書く）を並べて、研究の間隔、単価記録の関門、`sort { }` を直す費用、「買えるものがなく待つだけ」の区間を出す。`--human-save N`（研究が収入 N 秒分以内なら貯める）と `--human-pick biggest` で人間の前提を変えられる。いまの価格では、ボットのリリースが 17:08、人間らしい方針が 15:00、待つだけの区間は最長 80 秒だった。`--backdoor lanes,night,audit` を付けると、人間らしい方針 13:04、ボット 16:26。人間らしい方針はコードを読む・考える時間を数えないので、ボットより速く出る。人間の実時間はプレイテストで確かめる。

## 付録 A: prelude.rb（ruby.wasm 4.0.0 stdlib なし版と CRuby 4.0.5 で動作確認済み）

本体は `src/ruby/prelude.rb`。stdlib なしの ruby.wasm で動くよう、JSON と StringIO は使わない。中身の要点は次のとおり。

- `Yield` モジュールに鑑定の数え方（`tick`、上限を超えると `Yield::Overheat`。`Overheat < Exception` なので `rescue => e` で捕まらない）、バッチの入口 `run([box, limit, raw])`、デプロイの入口 `deploy(src, box = nil)` を置く。
- `run` は頭で `@ops`・`@polished`・`@heat` を 0 に戻し、`pack` の戻り値を `\x1f` 区切りの文字列 1 本にして返す（10.2 節）。
- `deploy` の間は `$stdout` / `$stderr` を `Log` に差し替え、戻り値は `"OK" US log` ／ `"ERR" US class US message US line US log`。ファイル名は `pack.rb`、入口は `pack` に決め打ち。
- `Ore = Data.define(:id, :color, :carat, :flaw)` に `Yield::Metered` を prepend し、属性を読むたびに鑑定を数える（6.1 節の数え方）。`polish` は `Yield.tick(Yield.heat_up)` で、研磨機の熱の数だけ鑑定する。
- `Yield.heat_up` は、`@heat` が整数で 0 以上・ここまで磨いた回数以下のときだけ +1 し、それ以外は 0 から数え直して、上がった熱を返す。`patched?` は `tick` と `heat_up` の再定義を見る。
- `Yield.cooled?`: 磨いた原石があり、`@heat` が整数でないか磨いた回数（`@polished.size`）と違えば true。worker が OK のバッチごとに読み、監査が冷やした分の研磨を数え直すのに使う。
- `Yield.polished`（public）は残している。直呼びは監査の研磨の下限で捕まる（6.1 節）。
- 裏口: `@lanes = 1`、`@memo`、合鍵（名前のないクラス。夜間ラインと残業はクロージャのローカル変数）を入れた `KEYRING` と `REPORT`（どちらも private_constant）、Yield の特異クラスの `method_missing`（private）と `respond_to_missing?`（SPEC-rubyist 4.1）。
